## The feed

**Endpoint, baked into the app at build time:**
`https://easybtx.com/updater/latest-node.json`
(`apps/node/src-tauri/tauri.conf.json` → `plugins.updater.endpoints`)

Deliberately **not** `releases/latest/download/…`: the node shares the
`EasyBTX-releases` repo with the miner, and GitHub's "latest" pointer is
repo-global, so it flip-flops between the two products. The feed file lives at
`site/public/updater/latest-node.json`; Astro serves `public/` verbatim, so it
goes live on Vercel when the site PR merges.

Because the endpoint is compiled in, **changing it strands every already-installed
app.** Historically `tauri.linux.conf.json` and `tauri.windows.conf.json`
overrode it with `latest-node-linux.json` / `latest-node-windows.json`, which
were never generated by anything and returned 404 forever — those two platforms
could not self-update at all. That is the root cause of the unexplained
"Windows 0.5.1 did not self-update" report. The overrides were removed in 0.6.0,
so 0.6.0 must be installed by hand on Windows and Linux; from 0.6.0 onward all
three platforms use the one working feed.

**One manifest, one version, a platform subset.** A *malformed* platform entry
breaks updates for everyone, Mac included, because Tauri validates the whole
manifest before it compares versions. An *absent* one is safe — but not for the
reason this file claimed until 0.6.6.

It does NOT yield a quiet "no update available". In tauri-plugin-updater 2.10.1
`get_urls` runs BEFORE the version comparison, so a client whose target key is
missing from a higher-versioned feed gets `Err(TargetsNotFound)`. What makes it
harmless is `main.ts` `updateCheck`: it only surfaces an error when the check was
MANUAL, so the automatic 6-hourly check swallows it and the client stays put,
downloading nothing. The visible cost is the **Check now** button, which reports
"Couldn't check right now — are you online?" to anyone on an omitted platform.
Expect a little support noise from whichever platform you leave out, and do not
mistake that report for a broken feed.

So a single-platform release still ships a feed carrying only that platform's
key, and the others stay on their last real build.

**Use the scripts. They verify; hand-assembly does not.** `gen-node-feed.py` and
`build-node-feed.sh` used to demand all three platforms, so the 0.6.2/0.6.3/
0.6.4 mac-only releases hand-wrote the feed and thereby skipped the minisign
verification those scripts exist to perform. Both now accept any non-empty
subset (`--mac` / `--linux` / `--win`) and verify every signature they are
given, against the app's own embedded pubkey. There is no longer a reason to
hand-assemble, and doing so silently drops the only check that catches a feed
signed with the wrong key.

```bash
# Linux-only release:
bash apps/node/scripts/build-node-feed.sh --version 0.6.5 \
  --linux dist/BTX-Node_0.6.5_amd64.AppImage
```

`gen-node-feed.py` DERIVES each URL from the version being published, so the
stale-key loop below cannot be expressed through it. It also refuses a signature
whose minisign key id is not the one baked into `tauri.conf.json`.

⚠ **The stale-key trap, on ANY single-platform release.** The manifest carries
ONE top-level `version` for all platforms. So when you publish a feed at a new
version, every platform key in it must point at an asset AT THAT VERSION.

Leaving another platform's key pointing at its older asset is the failure mode.
Publish `version: 0.6.5` with a `linux-x86_64` key while `darwin-aarch64` still
points at the 0.6.4 `.app.tar.gz`, and every mac client enters a permanent
update loop: it is offered 0.6.5, downloads the 0.6.4 bytes, verifies them,
installs them, still reports 0.6.4, and is offered 0.6.5 again on the next
check. The signature is valid, so nothing errors. It just never converges.

**Drop the other platform's key entirely instead.** Absent is the safe state:
those clients see "no update available" and stay where they are, which is
correct, because they already have the build you wanted them to have. A mac on
0.6.4 needs nothing from a Linux 0.6.5 release — its bundled btxd has been
`1e51f0d1` since 0.6.2.

| Target | Updater artifact |
|---|---|
| `darwin-aarch64` | `.app.tar.gz` (**not** the .dmg — that is manual-install only) |
| `linux-x86_64` | the `.AppImage` (same file users download) |
| `windows-x86_64` | the `-setup.exe` (v2 reuses it; not a `.nsis.zip`) |

## The engine freeze is OVER. v0.34.5 is the clean tag, and it is our pin.

This section said "Engine bumps are FROZEN, 0.34.5 is not tagged" until
2026-08-31, and for its whole life it was right. It is now history, kept short
so the lesson survives:

* Upstream's own release notes named a defect in every published 0.34.x
  through 0.34.4 (partitions, deadlocks, header stalls), and unreleased
  `f95aa706` recorded that those wrote poisoned `BLOCK_FAILED_*` marks which
  survive a binary upgrade. That is why we shipped nothing for weeks while
  users sat frozen: every available bump failed the "upstream itself calls it
  clean" bar.
* **v0.34.5 was tagged on 2026-08-30 and clears that bar.** It carries the
  `f95aa706` fix (`git tag --contains f95aa706` returns v0.34.5, measured),
  the poisoned marks clear automatically on start, the withdrawn stall
  recovery height is the disabled sentinel on every network, and it passes
  BOTH of our guards. It is `NODE_RELEASE_TAG` since 0.6.13 and ships to
  users in 0.6.15.

The durable rule stays, restated for the next freeze: **ship no engine bump
until a tag exists that upstream itself calls clean AND both guards pass on
the box cutting the release.** Our own checks are necessary, never
sufficient, and the changelog says which of the two bars a decision rested
on.

Two 0.34.5 specifics a release cutter needs:

* On 0.34.5 and newer, non-Metal hosts run CONSENSUS mode, not the trusted
  mirror: the engine admits a capable card by measurement at startup
  (verified on an RTX 3060: self-qualifies, advertises MATMUL_CONSENSUS),
  and the 1-of-1 mirror both requires an alarming override and depends on an
  attestation supply that measured dead. `crates/btx-core/src/node.rs`
  encodes this; do not hand a 0.34.5 host mirror flags.
* A host with no capable card starts degraded, follows headers, and stalls
  below the Epoch-A height. The release notes must say which machines
  validate and which only follow. Do not imply everyone is a validator.

### 2026-09-05: the pin moved PAST the newest tag, and why that was allowed

0.6.18 ships **0.34.6 from `release/0.34.6` at `9eb4e0050e08ea3ef768bac276dac9cbd2e84542`**,
and upstream has not tagged 0.34.6. That breaks the first half of the rule
above ("until a tag exists that upstream itself calls clean"), and it was
broken on purpose, by the owner, on a measurement rather than an argument:
on one box, same datadir, same arguments, only the binary changed, v0.34.5
connected 0.68 blocks/min against a chain producing 0.95 and fell behind for
good while reporting itself healthy; this build did 3.80, has held the tip on
the project's validator since 2026-09-02, and at least one other operator
(`109.199.124.187`, `/BTX:0.34.6/`) runs it. A release on v0.34.5 would have
shipped the fleet's biggest problem to every fresh install. The second half of
the rule held: **both guards passed on the box cutting the release**, against
that exact commit.

What that changed mechanically, so the next cutter is not surprised:

* `NODE_RELEASE_TAG` is still the NAME (`v0.34.6`: install directory, the
  version btxd reports, the guards' label). `NODE_RELEASE_COMMIT` beside it is
  the identity. Clear it when upstream tags 0.34.6 **at that commit**; if
  upstream tags a different commit, re-run both guards on the tag and compare
  trees before moving anything. The comment above the constants says the same.
* Both guards fetch source **by SHA** when `NODE_RELEASE_COMMIT` is set
  (raw.githubusercontent accepts a SHA where a tag would go). A branch name is
  never substituted. An explicit override argument is still taken literally.
* `engine_pin_ref` in `apps/node/scripts/lib/engine-pin.sh` returns the commit
  when there is one, else the tag; `btxd-linux.yml` checks that out. The
  download-based staging scripts (`stage-node-pkg.sh`, `stage-node-pkg-linux.sh`)
  cannot stage an untagged engine (no upstream tarball) and refuse via
  `assert_matches_engine_pin`; only the `-source` scripts work in this state.
* `node-win-installer.yml`'s guard compares `NODE_RELEASE_TAG` with the proven
  Windows btxd and will fail until a Windows btxd exists at this commit. That
  is the guard doing its job; Windows stays on 0.6.6 meanwhile.

### The fork check: necessary, never sufficient

`consensus.nMatMulStallRecoveryHeight = 199'299` is an ASERT re-anchor at a
height the chain had already passed. `pow.cpp` applies it with no version gate,
and `MatMulAsert` (`pow.cpp:3168`) compares `next_height` with `==`, so
divergence begins at exactly 199299.

| Tag | mainnet `nMatMulStallRecoveryHeight` | |
|---|---|---|
| v0.33.3 | absent | clean of this defect |
| v0.33.4, v0.33.4.1, v0.33.4.2 | `199'299` | 🔴 forked |
| v0.34, v0.34.1 | `199'299` | 🔴 forked |
| v0.34.2, v0.34.3, v0.34.4 | `std::numeric_limits<int32_t>::max()` | clean of this defect |

Introduced by `1c87fcd6` (2026-08-24), which merged as v0.33.4 via upstream PR
#119. Withdrawn by `1a58e07a` (2026-08-27), first shipped in v0.34.2.

⚠ **The guard this file used to print was vacuous.** It grepped
`consensus.nMatMulStallRecoveryHeight = ` and told you safe tags print
`std::numeric_limits<int32_t>::max()`. v0.34.1 prints that four times, right
after the line that partitions you, so a forked tag passed:

```
$ git grep -h "consensus.nMatMulStallRecoveryHeight = " v0.34.1 -- src/kernel/chainparams.cpp
        consensus.nMatMulStallRecoveryHeight = 199'299;
        consensus.nMatMulStallRecoveryHeight = std::numeric_limits<int32_t>::max();
        consensus.nMatMulStallRecoveryHeight = std::numeric_limits<int32_t>::max();
        consensus.nMatMulStallRecoveryHeight = std::numeric_limits<int32_t>::max();
        consensus.nMatMulStallRecoveryHeight = std::numeric_limits<int32_t>::max();
```

Use an inverted FAIL check. It matches only the forked value, so **any output at
all is a STOP** and a clean tag prints nothing:

```bash
git grep -h "nMatMulStallRecoveryHeight = 199" <tag> -- src/kernel/chainparams.cpp
# a line, exit 0  = FORKED, do not ship
# nothing, exit 1 = clean of this defect
```

Real output, run in `~/repos/btx` on 2026-08-28:

```
$ git grep -h "nMatMulStallRecoveryHeight = 199" v0.34.1 -- src/kernel/chainparams.cpp
        consensus.nMatMulStallRecoveryHeight = 199'299;
$ echo $?
0
$ git grep -h "nMatMulStallRecoveryHeight = 199" v0.34.4 -- src/kernel/chainparams.cpp
$ echo $?
1
```

`scripts/check-engine-tag.sh` runs this check against a candidate tag, and it is
stricter than the grep. It strips comment text and compares the assigned VALUE,
so a forked line cannot hide behind a comment that mentions the sentinel. It
requires EVERY assignment in the file to be the disabled sentinel. It fails when
it finds none at all, and it fails when the assignment count is not five, so a
line that stops matching cannot silently read as clean. Run it rather than
retyping the grep. It does **not** run the assumeutxo check below. Run that one
by hand.

⚠ **Always pass the tag: `scripts/check-engine-tag.sh <tag>`.** Run with no
argument it checks the pin in `commands.rs`, and today that exits 0 even though
the pin is forked, because `ACKNOWLEDGED_FORKED_TAG` at the top of the script
names it. That exit code is an acknowledgement of a known state, never a verdict
that the pin is clean. Read the output, not the exit code, and use
`ENGINE_TAG_GUARD_STRICT=1` if you want the pin judged on its merits.

Passing it proves one thing only: the tag is free of THIS defect. It says nothing
about the withdrawn assumeutxo bases, the deadlock, the header gap, or the
poisoned block marks, which is why the freeze above outranks it.

### Our users are FROZEN below 199299, not parked

This file used to say they were "safe only while parked below 199299". That was
wrong in kind, not degree. A frozen node is not a parked node. It is not
following the chain and it will not start again on its own.

Two populations exist in the field, read from a peer's live node on 2026-08-28:

- **Held below.** `/BTX:0.33.3/` peers sitting at 199297. They stop at the last
  block they can accept and stay there. A clean engine alone gets them moving.
- **Crossed.** `/BTX:0.33.4/` peers at 199303 and 199310, on the branch the
  withdrawn rule builds, which then died. **These need a one-time rollback as
  well as a new engine.** A new binary does not reorg a chainstate that has
  already split. Upstream's own guidance for this group is to wipe the datadir
  and sync from genesis, or load assumeutxo-191266 on a fresh datadir. The
  poisoned `BLOCK_FAILED_*` marks are a separate, additive problem: `f95aa706`
  says they were written by 0.34.0 through 0.34.4, so a node that crossed on our
  own v0.33.4.x engine does not have them. Do not cite them as the reason a
  0.33.4.x node needs a rollback.

Which side a user lands on follows from the engine their platform shipped. Mac
0.6.12 bundles v0.33.4.1 and carries the withdrawn rule, so mac is the only
platform of ours that can reach 199299 at all. Windows is on 0.6.6 with the
`1e51f0d1` pin, which predates `1c87fcd6` and does not carry the rule. Linux is
on the published 0.6.5, also clean of it. `apps/node/CHANGELOG.md` documents a
Linux 0.6.11 on the v0.33.3 tag, but that tag is not published on the releases
repo, so no Linux user has it. Neither of those two platforms is near 199299
anyway: both park at 191,713 first. Those peer version strings were observed on
the network. We did not measure our own installs.

Balances are unaffected in both populations. A node reads the chain, it does not
hold keys. Say that plainly in any user-facing note.

### How a frozen user actually recovers, and in what order

Added 2026-08-31 from an operator who ran a real 0.34.5 catch-up on an RTX 5080
and sent the numbers. Their measurements, not ours, and labelled that way.

**Upgrade FIRST, then attach a peer. The intuitive order does nothing.**

A 0.33.4.x node frozen at 199,29x will not unfreeze from being fed block bodies,
because its own fork choice never crosses the re-anchor. Block relay is
wire-version agnostic, so a 0.34.5 peer will happily serve it, and it will still
sit there. The engine has to change before any peer helps.

So the user-facing sequence is: update the app, let the new engine start, and
only then does peer quality matter.

**A clean frozen chainstate does not need wiping.** `loadtxoutset` creates a
separate snapshot chainstate alongside the existing background one rather than
replacing it, so a 199,29x chainstate that was never on a withdrawn base loads
the 203000 snapshot in place. The wipe in upstream Case B is specifically for a
poisoned base. Ours is not poisoned.

⚠ That paragraph is reasoned from assumeutxo mechanics by the same operator, who
was explicit that they ran 0.34.4 to 0.34.5 rather than 0.33.4 to 0.34.5 plus the
snapshot. Treat it as strong and unconfirmed until somebody runs that exact path.

**Catch-up speed is set by peers, not by the machine.**

```
per-block validation      4.65 to 4.81 s   RTX 5080
that alone would allow     ~775 blocks/h
actually achieved            58 blocks/h   263 blocks in 4.56 h
```

Seven and a half percent of what the hardware could do. Everything else was spent
waiting on peers to serve bodies. For a user around 5,600 behind that is roughly
four days poorly connected and roughly seven hours well connected, on the same
machine. Any duration in a release note has to carry that range, not a single
number, and has to say the slow case is about peers rather than their Mac.

**Tell users to keep the wallet closed while it catches up.** On that operator's
node, opening the wallet to read a balance slowed `ConnectBlock` enough that the
node fell behind the tip and began self-forking, and the wallet RPCs then hung on
`cs_main` so the balance was unreadable anyway. The panel warns about this above
50 blocks behind, and it advises rather than unloading anything itself.

**Do NOT pass `-cadenceburstmax=0`**, even though an operator who hit the cadence
hold will tell you to. It disables a real dump-and-run protection, and the hold is
already disarmed for a catching-up node: `kernel/chainstatemanager_opts.h:331`
says IBD, a stale tip, and recovery_escape each disarm it so partition catch-up
runs at body-download speed. They hit it because their tip was live when the
majority surged past them. Different state, opposite answer.

**Before any restart, check free disk.** Their worst moment was a node that
crashed on "Disk space is too low", failed its flush on stop, and could not
restart because the disk was full. `run_setup_pipeline` already guards this and
distinguishes a fresh install from a resume, so keep that guard rather than
trusting that a resume needs little space.

### What a release must check that these steps do not

**A candidate tag's assumeutxo table must not carry a base upstream has
withdrawn.** v0.34.2, v0.34.3 and v0.34.4 all still compile both of them:

| Height | `blockhash` |
|---|---|
| 199'299 | `f12a27d01a4b5a1710efa4497adf6f4c7da311d1c7b4f6a79cbf80f0b3110ec5` |
| 199'300 | `ff80e6299692a63345674a23b0638658c737529d12e78fc7f42afb3812afc9eb` |

They are dropped only in the unreleased 0.34.5. Check a candidate with:

```bash
git show <tag>:src/kernel/chainparams.cpp \
  | awk '/^        m_assumeutxo_data = \{/{f=1} f && /\.height = 199/{print} f && /^        \};/{f=0}'
# any 199'299 or 199'300 line means the tag ships a withdrawn base
```

**Our own snapshot pin is safely below the split, so this is a check for future
pins rather than a live problem.** `snapshot_spec()` in
`apps/node/src-tauri/src/commands.rs` returns `v0_33_2_spec()` from
`crates/btx-core/src/snapshot.rs`, whose `anchor_height` is `179_000`. Both read
and confirmed 2026-08-28. Any future release that moves that pin forward must
land it on a base the candidate engine still carries and upstream has not
withdrawn.

Full reasoning in `LEARNINGS-mac-mining.md` §19.

**Also verify the tag's own seal before staging**, which catches a binary built
from a tree that is not the tag:

```bash
git ls-tree -r --full-tree <tag> -- CMakeLists.txt cmake src contrib/matmul-v4 \
  | grep -v 'matmul_v4_rc_production_golden_manifest.data$' | shasum -a 256
# compare against field 9 (PIPE separated) of line 2 of that tag's golden manifest
```

🔴 **"Must equal" is wrong, and following it literally will block a good release.**
The manifest's seal field pins the tree the GOLDENS were produced from, not the
tree that ships them. When upstream carries a manifest forward unchanged, the
seal keeps pointing at the older tag and the check mismatches for a benign
reason.

Measured 2026-08-31 on v0.34.5:

```
computed seal v0.34.5                       610209dae713ba39d411bb8338ad2026...
field 9, line 2 of v0.34.5's own manifest   b9c6e4852ab1dc1cc7f998c7199a16f4...
computed seal v0.34.4                       b9c6e4852ab1dc1cc7f998c7199a16f4...   <- match
```

The v0.34.5 manifest is **byte identical** to v0.34.4's (both sha256
`d317a374...`), and its field 8 is `855f220b`, the "release: freeze 0.34.4"
commit. So v0.34.5 inherits 0.34.4's goldens verbatim.

**The correct check is therefore two steps.** Read field 8 of the line, which
names the commit the goldens were sealed against. Compute the seal of THAT ref
and require it to equal field 9. Then satisfy yourself the candidate tag has not
changed anything the goldens depend on, which for 0.34.4 to 0.34.5 is true
because the manifest did not move. A raw mismatch between the candidate tag and
field 9 is only evidence of a dirty tree when field 8 names the candidate tag
itself.

```bash
# the two-step form
MF=$(git show "<tag>":"src/matmul/matmul_v4_rc_production_golden_manifest.data" | sed -n 2p)
SEALED_AT=$(echo "$MF" | awk -F'|' '{print $8}')   # commit the goldens were sealed at
WANT=$(echo "$MF" | awk -F'|' '{print $9}')        # seal recorded for it
git ls-tree -r --full-tree "$SEALED_AT" -- CMakeLists.txt cmake src contrib/matmul-v4 \
  | grep -v 'matmul_v4_rc_production_golden_manifest.data$' | shasum -a 256
# THIS must equal $WANT
```

**Better than the seal check: compare the staged binaries to the official
release byte for byte.** The seal check tells you the GOLDENS are authentic. It
tells you nothing about the binary you are about to ship. This does:

```bash
curl -sL -o t.tar.gz "https://github.com/btxchain/btx/releases/download/<tag>/btx-<v>-arm64-apple-darwin.tar.gz"
shasum -a 256 t.tar.gz          # must match the release SHA256SUMS line
tar xzf t.tar.gz -C official/
for f in libexec/btxd.real libexec/btx-cli.real bin/btxd bin/btx-cli; do
  shasum -a 256 "official/btx-<v>/$f" "apps/node/src-tauri/resources/node-pkg/$f"
done
```

Done for the 0.6.13 staging on 2026-08-31. Tarball sha256
`67e5ed639d2fcc05f8c40d9a945e447140312b7c7505a85c41452e851e98946e` matched the
release `SHA256SUMS`, and all four staged binaries were byte identical to the
ones inside it. That is a stronger statement than the seal check can make and it
is the one worth recording per release.

**And verify `libexec/btxd.real`, never `bin/btxd`** — since 0.34.1 the latter is
a shell wrapper and `otool -L` on it returns nothing while looking clean
(`LEARNINGS` §21).

## Before you cut anything on the 0.34 engine

Read from the 0.34 draft (btxchain/btx#123) at freeze commit `16c7e1ee` on
2026-08-27. **Re-verify every line against the real tag**, this was a moving
draft. Full reasoning in `LEARNINGS-mac-mining.md` §18.

🔴 **This is not a tag move. It needs a code change first.** 0.34 refuses a
mainnet trusted mirror with `M<2` or `N<2` unless `-allowsinglekeytrustedmirror=1`
is passed. `crates/btx-core/src/node.rs` ships three keys with
`-matmultrustedthreshold=1`, so the 0.34 engine would be **refused at init on
every Mac that takes the mirror path**. Decide before bumping: move to M=2 (the
right end state, and it means both signers must attest every block, so it wants
a soak), or pass the override deliberately and say so in the changelog.

Also expect:

- **ZMQ is on by default in 0.34**, static `libzmq.a` preferred on macOS, and
  packaging refuses a btxd that fails upstream's
  `scripts/release/verify_release_btxd.py`. Our `build-ship` currently has
  `WITH_ZMQ:BOOL=OFF`, so plan a reconfigure and re-run that verifier before
  staging.
- **A fresh trusted mirror cannot bootstrap on 0.33.4.x** (`LEARNINGS` §16). If
  0.34 does not fix it, a clean install on an M5 still ends at "node never became
  ready". Test a genuinely empty datadir before shipping, not an upgraded one.
- `-matmulvalidation=relay` is new: ADDR-only discovery, no attestation serving.
  A candidate Keeper profile for Macs that cannot validate.

## Steps

1. **Bump the version** in `apps/node/package.json`, `package-lock.json`,
   `src-tauri/tauri.conf.json`, `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock`,
   plus `apps/node/CHANGELOG.md`.

   ⚠ **The btxd pin: do not move past `1e51f0d1`.** It is no longer all three
   platforms, as of 2026-08-28. It governs the Windows 0.6.6 and Linux 0.6.5
   builds, which are the published ones on those platforms. Mac has moved off
   commit pins entirely and bundles a release tag, v0.33.4.1 in 0.6.12, so this
   note does not describe the mac path any more.
   `f3098105` and everything after it (checked through `3455bbdc`) added
   `RefuseUnverifiableMatMulConsensusStartup`: a consensus-mode node with no
   qualified MatMul device **exits during init** instead of running.
   `-matmulrcexecution=auto-fallback`, which `node.rs` passes every
   non-Apple-Silicon host, does not avoid it — the refusal keys on the device,
   not the mode. Measured side by side on a GPU-less machine: v0.33.2 starts,
   `1e51f0d1` starts, `2bfd359b` refuses. Newer commits carry real fixes we want,
   so re-check this each time, but take nothing that keeps the refusal.

2. **Windows btxd first — it is the long pole.** Upstream publishes *no* Windows
   binaries in any release, so `.github/workflows/btxd-windows.yml` is the only
   source that exists.

   ⚠ Dispatch it with **`btxchain_ref=<btxd commit SHA>`** — the same COMMIT SHA
   rule step 3 states for Linux, and for the same reason: artifact names cannot
   contain `/`, so a branch name fails the upload after a full build. It is
   currently `1e51f0d1ccc594b8fe215a6af3dcc7c118d7d1ca`.

   This step used to read `btxchain_ref=v<node version>`, which is wrong twice
   over: the node's version (0.6.x) and btxd's ref are unrelated namespaces, and
   **the input's default is `v0.33.2`** — upstream's fork-blind tag, the one that
   parks a node at 184,999. So following it literally, or leaving the field
   blank, silently builds exactly the binary this whole train exists to replace,
   and every downstream version gate still reports `v0.33.2` and waves it through.

   Then set **all four** pins in `node-win-installer.yml` together:
   `PROVEN_BTXD_RUN_ID`, `PROVEN_BTXD_ARTIFACT`, `PROVEN_BTXD_VERSION` and
   `PROVEN_BTXD_TAG` — the artifact name is minted from the ref, so moving only
   the run id downloads nothing. Confirm the regtest smoke job passed first.
   Expect friction: the mingw `NO_STRICT` recipe is fragile against upstream's
   consteval usage.

3. **Linux** via `node-linux-installer.yml` (`workflow_dispatch`, or any PR
   touching `apps/node/**` / `crates/btx-core/**`). Since 0.6.5 it consumes a
   SOURCE-BUILT btxd from `btxd-linux.yml` rather than an upstream tarball,
   because upstream publishes no Linux asset for a branch commit and v0.33.3 is
   still untagged. Dispatch `btxd-linux.yml` with the **commit SHA** (artifact
   names cannot contain `/`), then move `PROVEN_BTXD_RUN_ID` and
   `PROVEN_BTXD_ARTIFACT` together. It executes the bundled btxd from both the
   `.deb` and `.AppImage` layouts, which is what proves the `$ORIGIN` library
   vendoring survived packaging.

4. **Mac locally** — there is no Mac node CI:
   ```bash
   cd apps/node && TAURI_SIGNING_PRIVATE_KEY="$(cat ~/.tauri/easybtx.key)" \
     TAURI_SIGNING_PRIVATE_KEY_PASSWORD="" npx tauri build --bundles app,updater
   ```
   The signing key has an **empty password**; the variable must still be set.
   `build.rs` refuses a release build when the node package was never staged.

   ⚠ **Do NOT run `stage-node-pkg.sh` for a release that ships a source-built
   btxd — which is every release since 0.6.2.** That script stages an *upstream
   release tarball*: with no `~/btx-node-research/btx-0.33.2` present it
   downloads upstream v0.33.2, `rm -rf`s the staged tree and replaces
   `1e51f0d1` with the fork-blind binary that parks at 184,999. Its version gate
   does not catch this, because `1e51f0d1` also reports `v0.33.2`. The tree for
   a source-built node comes from `stage-node-pkg-mac-source.sh` instead, and
   has a different shape (`bin/` + `bin/lib/`, no `libexec/`), so the two are
   not interchangeable.

   In practice the tree is usually **already staged and correct** from the
   previous release. Leave it alone and prove it byte-for-byte instead:
   ```bash
   tar -xzf ~/Desktop/BTX-Node-<prev>-release/BTX-Node_<prev>_aarch64.app.tar.gz -C /tmp/prev
   diff <(cd "/tmp/prev/easyBTX Node.app/Contents/Resources/resources/node-pkg" \
            && find . -type f -exec shasum -a 256 {} \; | sort -k2) \
        <(cd apps/node/src-tauri/resources/node-pkg \
            && find . -type f -exec shasum -a 256 {} \; | sort -k2)
   ```
   Then re-check the SHIPPED bundle after building, not just the staging dir.

   `--bundles app,updater` is deliberate: the bundled `bundle_dmg.sh` fails in a
   headless shell, and a run that includes `dmg` can die there *after* skipping
   the updater artifacts. Build app+updater, then make the .dmg with `hdiutil`
   (`Applications` symlink + the `.app`, `-format UDZO`), which is exactly what
   the 0.6.4 dmg contained.

   ⚠ **The key is not only on the mac, and not only at that path.** On the Linux
   publishing machine (the 3060 box) the same key is at the repo root as
   `updater.key`. Searching only `~/.tauri/easybtx.key` there produced a
   confident wrong answer — that the machine could not sign at all — and nearly
   sent a finished release to another computer for no reason.
   `build-node-feed.sh` honours `EASYBTX_UPDATER_KEY`; verify whichever file you
   find by signing a throwaway and checking its key id matches the pubkey in
   `tauri.conf.json` (`5D4392DA73BCC2A2`).

   ⚠ **On Windows/WSL no single shell has the whole toolchain**: `npx tauri` runs
   Windows-side, `minisign` only exists inside WSL, so `build-node-feed.sh`
   cannot complete there. Do its three steps by hand for the same guarantees:
   sign with `npx tauri signer sign -p ""`, verify with `minisign -V` in WSL,
   then `gen-node-feed.py`, which independently re-checks the signature's key id.

5. **Names are already the release convention.** The Linux and Windows
   workflows rename the bundler's `easyBTX Node_<ver>_…` outputs to
   `BTX-Node_<ver>_<arch>.<ext>` *before* hashing, so `SHA256SUMS` lists the
   names that ship. Do not rename anything after download: a renamed asset no
   longer matches its sums line and the publish gate refuses it. The mac
   tarball is built by hand and has no CI sums file. The gate does not cover
   it, and this page must not be read as saying it does.

6. **Build the feed** (signs the keyless CI artifacts locally and
   minisign-verifies each one against the app's embedded pubkey
   `RWSiwrxz2pJDXR4AchfYB5DQzvD8VbIE3D87Ft4D/km76xZIikK6XE9y`). Pass only the
   platforms this release actually ships:
   ```bash
   bash apps/node/scripts/build-node-feed.sh --version <ver> \
     [--mac <mac.app.tar.gz>] [--linux <linux.AppImage>] [--win <win-setup.exe>] \
     [--notes "<notes>"]
   ```
   It **writes** `site/public/updater/latest-node.json`. Never hand-edit that file.
   Every platform key it emits points at an asset at `<ver>`, so those assets
   must be attached to the release in step 7 before this feed is deployed in
   step 8.

7. **Publish.** This is now a script, `apps/node/scripts/publish-node-release.sh`,
   and you should use it rather than the commands below. It does the draft ->
   upload -> re-download -> verify -> flip sequence in the right order, refuses
   an artifact with no signature, refuses one whose signature does not verify
   against the pubkey in `tauri.conf.json`, and checks afterwards that the
   repo-global Latest pointer did not move.

   ```bash
   # checks everything, creates nothing:
   apps/node/scripts/publish-node-release.sh <ver> <asset-dir>
   # then, once it is green:
   apps/node/scripts/publish-node-release.sh <ver> <asset-dir> --publish
   ```

   The manual sequence, kept because you should understand what the script does:

   ```bash
   apps/node/scripts/publish-node-release.sh <version> <asset-dir>            # checks only
   apps/node/scripts/publish-node-release.sh <version> <asset-dir> --publish
   ```
   Two positionals, not the flag interface an earlier draft of this page
   described. The asset dir holds the artifacts, their `.sig` files, and the
   gate run's `SHA256SUMS`.

   It performs every check this step used to ask a human to remember: the
   artifacts must be listed in the gate run's `SHA256SUMS` with matching hashes
   (a rebuild after the gates is refused; a file that is merely NEWER than the
   sums while still matching them is a copy, not a rebuild, and is called out
   rather than refused), the
   updater signature must verify against the pubkey the app embeds, the release
   is created as a draft and only flipped live once its assets are attached,
   every asset is re-downloaded and compared after publishing, and
   `/releases/latest` is re-read at the end. Run it WITHOUT `--publish` first:
   that does every offline check, peeks at `/releases/latest` if `gh` happens
   to be installed, and exits green, on a box without `gh` too.

   The SHA256SUMS gate is the one the signature cannot stand in for. A signature
   proves "these bytes, signed by our key", which is equally true of a rebuild
   made ten minutes after the gates went green. Byte-identity to the run's
   SHA256SUMS is what connects "the gates passed" to "this is what ships".

   ⚠ It needs `gh` from the API half onward, and the publishing box has neither
   `gh` nor `jq` (measured 2026-09-04, both sides of the WSL boundary). The
   offline half — the version check, the signatures, and the SHA256SUMS gate —
   runs anywhere, deliberately, so those checks are usable on the box that
   cannot finish the job. Finishing it needs `gh` installed, or the REST
   sequence below run by hand.

   `--latest=false` is **mandatory** — otherwise the node release steals the
   repo-global "Latest" pointer and breaks the *miner's* updater. The script
   always sends it and fails if a node tag captured the pointer anyway; if you
   are ever publishing by hand, check `/releases/latest` yourself.

   The REST calls the script makes, which is also how 0.6.5 went out by hand.
   **Create it as a draft, attach the assets, then flip it live**, so there is
   never a window where the tag resolves but the files 404:
   ```
   POST /repos/MendeMatthias/EasyBTX-releases/releases
        {"tag_name":"node-vX.Y.Z","draft":true,"make_latest":"false", ...}
   POST https://uploads.github.com/.../releases/<id>/assets?name=<file>   (per asset)
   PATCH /repos/.../releases/<id>   {"draft":false,"make_latest":"false"}
   ```
   `make_latest` is the **string** `"false"`, not a boolean.

   Then verify against the RELEASED bytes, never the local copies you just
   built: re-download the asset and its `.sig`, `minisign -V` it under the
   embedded pubkey, and `sha256sum -c` the published `SHA256SUMS`. A signature
   that only ever verified locally proves nothing about what users will fetch.

8. **Merge the site PR** so Vercel deploys the new feed — and only AFTER the
   GitHub release is live with every asset returning 200, or easybtx.com serves
   download buttons that 404.

   Pins live in `site/src/pages/node.astro`: `REL_CURRENT` + `relPage` +
   `dl.mac` + `dl.win` move on a **mac/windows** release, `REL_LINUX` +
   `relPageLinux` + `dl.appimage` + `dl.deb` move on a **Linux** one. Never both
   from one release unless it genuinely carries all three platforms.

   ⚠ `site/src/pages/node/how-to.astro` hardcodes ONE version, and it is the
   **Linux `.deb` filename**. It moves on a Linux release ONLY. This step used to
   name that file flatly as a "version pin", which on a mac/windows train reads
   as an instruction to bump it — and bumping it points the `apt install` command
   at a `.deb` that release never built.

   The node changelog page needs no edit: `site/src/pages/node/changelog.astro`
   imports `apps/node/CHANGELOG.md?raw` at build time, and there is no localized
   copy. It publishes the new entry as "LATEST" the moment the site deploys,
   which is another reason not to merge ahead of the release.

## Verifying before you trust it

- `curl -s https://easybtx.com/updater/latest-node.json | jq .version`
- Confirm the released asset bytes match what was signed (sha256 the downloaded
  file against the local build).
- Observe a real upgrade: quit and reopen an older app — the check fires on
  launch, otherwise within 6 hours.

## Cutting a release from CI

The four release workflows live here now, alongside the two gates. They were
ported from the private monorepo on 2026-09-04, and the Linux pair was brought
forward from the v0.33.2 era in the process — as ported they built an engine
with **no CUDA backend**, which is the one mistake that produces a Linux node
that syncs, holds peers, reports itself healthy and cannot validate.

| workflow | what it does |
|---|---|
| `btxd-linux.yml` | builds btxd + btx-cli from a btxchain/btx tag **with CUDA**, on ubuntu-22.04, proves the tree was pristine, proves the kernels are in the binary, smokes it on regtest, uploads the artifact |
| `node-linux-installer.yml` | downloads that artifact, stages it, runs the suites, builds the AppImage and `.deb` |
| `btxd-windows.yml` | the Windows engine build |
| `node-win-installer.yml` | the Windows installer |

**The engine pins are empty on a fresh checkout, and that is deliberate.** The
installers download their engine from a specific Actions *run id*, and a run id
only resolves inside the repository the workflow runs in. The values these
carried in the private monorepo named runs that do not exist here. Inheriting
them would have failed at the download step with a message about a missing
artifact, which reads like a transient error and is not one.

So the first release cut from this repository runs in this order:

1. **Dispatch `btxd-linux.yml`.** Leave its inputs blank: it reads
   `NODE_RELEASE_TAG` out of `commands.rs` through
   `apps/node/scripts/lib/engine-pin.sh`, so the engine it builds is the engine
   the app will provision, with no second place to keep that number.
2. **Read its log, do not just look at the tick.** Two steps matter more than
   the rest: *Prove the tree is PRISTINE* and *Prove the CUDA kernels are
   actually in the binary*. The second one is the gate that did not exist
   before; it lists the architectures found in the ELF and fails if any
   requested one is missing.
3. **Set the pins** in `node-linux-installer.yml`: `PROVEN_BTXD_RUN_ID` to that
   run, `PROVEN_BTXD_ARTIFACT` to its artifact name, and optionally
   `PROVEN_BTXD_COMMIT` so the guard can prove identity. Two different commits
   can report the same version string, so the version is not an identity.
4. **Dispatch `node-linux-installer.yml`.** It re-runs both suites, stages,
   re-checks that the staged engine carries GPU kernels, and builds the bundles.
5. **Then the steps above**: sign, `publish-node-release.sh`,
   `build-node-feed.sh`, the site PR.

⚠ **These workflows have not yet cut a shipped release.** 0.6.15 through 0.6.18
were built by hand on an Ubuntu 22.04 box using the procedure in the next
section, and this CI is that procedure transcribed rather than a path with a
track record. Compare the first binary it produces against a known-good hand
build before trusting a release to it. The hand procedure below stays the
authority until CI has earned the job.

## Rebuilding the Linux release from nothing, so it never needs re-fixing

Everything below was executed end to end on the Windows box's WSL Ubuntu
22.04 on 2026-08-31 and 2026-09-01 for 0.6.15 through 0.6.17, and again on
2026-09-05 for 0.6.18 (the untagged 0.34.6 pin; deviations noted inline). It assumes
only: a checkout of this repo, a clone of btxchain/btx with tags, CUDA 13.3
(nvcc 12.6 segfaults on the tree), and the updater key. Build on the OLDEST
glibc the fleet runs (22.04, glibc 2.35); the official Linux binaries need
2.38 and will not run there, which is why we build at all.

1. Engine, from a PRISTINE worktree at the pinned ref (the provenance canary
   fails on any dirty file and the node then runs while silently not
   validating). The ref is the tag, or for an untagged pin the
   `NODE_RELEASE_COMMIT` SHA; `engine_pin_ref apps/node` prints it:

   ```
   git -C <btx-clone> worktree add --detach ~/btx-ship "$(. apps/node/scripts/lib/engine-pin.sh; engine_pin_ref apps/node)"
   # 0.6.18: 9eb4e0050e08ea3ef768bac276dac9cbd2e84542
   cd ~/btx-ship
   cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Release \
     -DBUILD_DAEMON=ON -DBUILD_CLI=ON \
     -DBUILD_UTIL=OFF -DBUILD_TX=OFF -DBUILD_WALLET_TOOL=OFF \
     -DBUILD_GUI=OFF -DBUILD_BENCH=OFF -DBUILD_TESTS=OFF -DBUILD_FUZZ_BINARY=OFF \
     -DENABLE_WALLET=ON -DWITH_SQLITE=ON -DWITH_ZMQ=ON \
     -DCMAKE_IGNORE_PATH=/mnt/c \
     -DCMAKE_CUDA_COMPILER=/usr/local/cuda-13.3/bin/nvcc \
     -DCMAKE_CUDA_ARCHITECTURES="75;86;89;120"
   ninja -C build
   ```

   Wallet ON and sqlite ON, or the app's wallet is dead. The arch list gives
   SASS for Turing through Blackwell (an extra sm_100 arrives via upstream's
   own isolated MXFP4 rules). Verify `BUILD_GIT_DIRTY 0` and that
   `BUILD_GIT_SOURCE_TREE_FINGERPRINT` equals the tag's seal in
   `build/src/bitcoin-build-info.h` before going further (0.6.18's engine:
   `BUILD_GIT_COMMIT "9eb4e0050e08"`, fingerprint `a7bf4bd74375b269…`).

   Two traps hit on 2026-09-05 that the staging script's header already warns
   about and that still cost two failed configures: `cmake` on the WSL box is
   pip-installed under `~/.local/bin` and is not on a non-login PATH; and WSL
   appends the Windows PATH, so cmake found anaconda's `LibeventConfig.cmake`
   under `/mnt/c` despite `-DCMAKE_IGNORE_PATH=/mnt/c`. What worked: a
   Linux-only PATH (`$HOME/.local/bin:/usr/local/cuda-13.3/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`),
   `-DCMAKE_IGNORE_PREFIX_PATH` on the anaconda directories as well, and
   `rm -rf build` before re-configuring; a half-configured build dir keeps the
   bad cache.

2. Stage into the app: `apps/node/scripts/stage-node-pkg-linux-source.sh
   ~/btx-ship/build v0.34.6`; the second argument is the version btxd REPORTS,
   i.e. the tag name, not the commit. It vendors the whole non system library
   closure (including the ~490 MB cuBLASLt) with ORIGIN rpaths and refuses
   anything unresolved.

3. App: in a NATIVE ext4 checkout (never /mnt/c, never shared node_modules),
   `npm ci`, the three test suites, then `NO_STRIP=true cargo tauri build`.
   NO_STRIP keeps the GPU kernels intact through AppImage packaging.

4. Gates, always on the EXTRACTED bundles, never the staging tree:
   `.btxd-version` reads the pinned tag name, the bundled btxd and btx-cli execute under
   `env -u LD_LIBRARY_PATH PATH=/usr/bin:/bin`, ldd resolves inside the
   tree, cuobjdump lists every pinned architecture (sm_75/86/89/120, plus
   upstream's own sm_100; the vendored cuBLASLt contributes more, nine in all
   on 0.6.18), and both engine guards exit
   0 with their OK text actually read.

5. The test that catches what clean rooms cannot: upgrade a REAL datadir
   from the mirror era. The engine persists settings in the datadir's
   btx_rw.conf and loads them regardless of -conf; 0.6.15 died on exactly
   that. The app passes -matmulvalidation=consensus explicitly since 0.6.16,
   and any future flag intent should likewise be explicit, never the absence
   of a flag.

6. Sign with `cargo tauri signer sign -f <updater.key> -p ""` (empty
   password), verify with `apps/node/scripts/verify-updater-sig.py`, publish
   with `apps/node/scripts/publish-node-release.sh` (authenticates through `gh`,
   which it never prompts for; refuses bytes the gates did not produce, refuses
   unsigned artifacts, `make_latest=false` always, re-downloads and compares
   after upload), and only THEN move
   `site/public/updater/latest-node.json` and the site pins, regenerating
   the feed with `gen-node-feed.py` so every signature is verified against
   the app pubkey.

   Two things from the 0.6.18 gate run, for whoever scripts step 4: the
   bundle path contains a space (`usr/lib/easyBTX Node/…`), so never
   word-split `ldd` output; and `cuobjdump` exits 255 on an ELF with no CUDA in
   it, which is the one exit status that makes `xargs` abort the whole run.
   Loop with `find -exec sh -c '… || true'` instead. And for step 6 on a box
   without `gh`: the live half of `publish-node-release.sh` is four REST
   calls in the same order (create DRAFT with `make_latest` the STRING
   "false", upload, re-download every asset and byte-compare against
   SHA256SUMS, PATCH `draft=false`), then assert `/releases/latest` is still
   the miner's. On Git Bash, `curl -o /dev/null` fails with exit 23; write to
   a real file.

Numbers with a shelf life (sizes, heights, seed lists) live in the code and
the changelog, not here. This section is the procedure, and the procedure is
what makes the next engine bump a rebuild instead of a rescue.
